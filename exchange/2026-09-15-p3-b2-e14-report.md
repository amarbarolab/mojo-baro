## Result: PASS at N=3, FAIL at N=10, on the identity gate the brief specifies

Identity is the gate, not task accuracy, per the brief: each follower's
`KV`-arm generated ids must equal that same follower's `Text`-arm generated
ids, token for token (`Text` is our own engine doing a full fresh re-prefill
of document + that follower's question, which is the only operational
meaning "what the reader itself would have produced" can have without a
second independent implementation, same reasoning E12-long used for its own
T-vs-KV gate).

**The N=10 FAIL is real and reported as such, not softened.** One follower
of ten (`q08`) has a token that differs between the two arms in the raw
64-token generated window, at position 62 of 64. Read in full in the
receipt: both arms' trimmed answers are identical and correct (`5105164`),
and the divergence is in continuation text generated after the real answer
and its stop token, the same reduction-order-divergence class E12-long's own
checker already caught once and explained (KV's restored state comes from
the reader's decode path, `Text`'s from a fresh prefill; near-tied logits
can differ by floating-point order after both paths have already agreed on
the actual answer). This does not overturn the primitive E12-long proved; it
is the frozen gate, applied at N=10 instead of N=1, catching the same class
of thing again. Per the brief's own instruction ("a follower that answers
correctly but differs in tokens is a FAIL"), N=10 is FAIL, stated plainly.

**The frozen wall-clock prediction did not hold, and the reason is good
news, not a mistake.** `docs/prefill-long-ctx-2026-09-11.md`'s prefill-GEMM
optimization (2.54x faster prefill at 32k) landed after E12-long's numbers
were written and is already in this tree, so the reader's one-time 32k
prefill measured 17.6 s, not the predicted 43.71 s, and every arm built on
top of it is faster than predicted. The one risk the preregistration stated
plainly in advance ("the KV arm may not even beat llama.cpp's naive
re-prefill at N=3") did not materialize: KV beat llama.cpp's total at both
N=3 (1.68x) and N=10 (3.70x).

## Why a new tool, not `bench_latent_handoff.mojo`

The brief said reuse the existing harness and mint/ingest path unless it
cannot express the shape, and say what changed. Two separate problems, both
checked before writing anything:

1. **Shape.** `bench_latent_handoff.mojo`'s per-item loop calls
   `reset_and_load` on the producer with each item's full context every
   item; `BARO_E8_SHARE_A` only reuses a producer decode within one item's
   arms, never across items. E14 needs the reader to prefill exactly once
   across all N followers, which this loop cannot express without
   restructuring its core per-item assumption.
2. **It does not currently build.** Confirmed by attempting its build
   (`./.venv/bin/mojo build bench/bench_latent_handoff.mojo ...`) before
   writing anything new: `WindowCfg` gained `dump4`, `dump_layer`, and a
   `sample: SampleParams` field, and `Chain.__init__`/`Chain.save` gained a
   `packdir` argument and `pinned`/`boundary` flags, all since this file was
   last touched. It is on `tools/ci-checks.sh`'s skip list for an unrelated
   reason (external grammar package), which is why this had gone unnoticed.

New tool: `bench/e14-handoff.mojo`, built directly against the current
engine API. The mint/ingest call shapes (`mint_kv_latent`, `ingest_kv_latent`,
`mint_chain_slot`, `ingest_into_chain`, `Chain(ctx, cap, packdir)`,
`Chain.save(..., pinned, boundary)`) are copied from `bench/latent_ingest_bench.mojo`,
which does build clean against this tree today (confirmed the same way) and
is the more current reference; the `WindowCfg`/prefill-loop shape is copied
from `kernels/test_prefix.mojo` (also builds clean, part of `run-tests.sh`),
not from the stale bench file. Both were read in full before writing a line
of the new tool, not guessed from the broken one.

Mid-session, `dfd65cd` (coordinator, `serve(moe): BARO_EXPERTS`, unrelated to
E14, landed for B4 stage 2) added `WindowCfg.expert_trace`, transiently
breaking this tool's own `make_cfg` the same way it broke every other
hand-written call site (`bench/bench_hidden_dtype.mojo`,
`kernels/test_prefix.mojo`, `kernels/test_realign.mojo`); fixed here with
`expert_trace=False` and confirmed clean at `2431838` (the coordinator's own
fix-up commit for the other call sites), `tools/ci-checks.sh` and
`./run-tests.sh` both green at that commit before this lane's commit.
`bench_latent_handoff.mojo`'s `Chain(ctx, kv_cap)` break (missing `packdir`)

## What ran, and where

- `bench/e14-data.py`: task set generator, one 32k-token document (31968
  measured) with 10 embedded magic-number needles, 10 follower questions,
  adapted from `bench/ruler/gen.py`'s `niah_multikey` (N needles/N queries
  sharing one document instead of 3 needles/1 query).
- `bench/e14-handoff.mojo`: the KV and Text arms, one reader prefill, N
  followers per invocation.
- `bench/e14-llama-prep.py` + `bench/e14-llama-run.sh`: the llama.cpp arm,
  adapted from `tools/llama-ref-run.sh` (which posts one prompt N times) to
  post N different prompts instead; also fixed a real bug along the way
  (a 32k-token prompt as an inline `curl -d` argument overflows the shell's
  argument-length limit at this size, fine at the original script's 8k;
  switched to `curl --data @file`).
- `bench/e14-check.py`: the identity gate and wall-clock table, reads the
  Mojo tool's raw output plus the llama.cpp timings.

Split into two 5-follower Mojo runs (`.work/e14/doc-part1.json` and
`doc-part2.json`, same document, disjoint questions) because a single
combined N=10 run's Text arm alone would take about 7.6 minutes, over the
brief's 5-minutes-per-arm limit; each part's full run (reader + 5 KV + 5
Text) stayed under 5 minutes. The N=10 wall-clock totals use one
`reader_prefill_s` (from the first part), matching what a real single run
would pay once; the second part's own reader prefill (17.249 s, consistent
with the first part's 17.565 s) is reported only as a receipt that the two
runs agree, never summed into a total. `bench/e14-check.py` does this
arithmetic explicitly when given both raw files, documented in its own
docstring.

`results/e14/` was created by mistake early on, mirroring the existing
`results/e8/` convention without checking the standing rule; both raw run
outputs were moved to `.work/e14/` and the empty directory removed. Nothing
under `results/` is part of this lane's deliverable.
