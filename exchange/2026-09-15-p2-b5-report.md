## What was built

`POST /v1/fork`: one shared `prompt` (token ids or a string, same shape
`/v1/completions` already accepts) plus a `branches` array, each with its
own `max_tokens`/`stop`/sampler fields (temperature, seed, top_p, ...).
Branches run sequentially against the one engine (it already serializes
one request at a time); branch 1 always prefills and saves a checkpoint at
the prompt's own end position (unconditional, `serve/engine.mojo:593-599`),
every later branch's identical prompt hash-matches it and restores instead
of re-prefilling (`serve/prefix.mojo:230-241`, also unconditional, already
true for any two requests sharing a prompt, fork endpoint or not).

Chose a dedicated endpoint over `n` on `/v1/completions`: OpenAI's `n`
means N completions of one request with the *same* sampler settings; B5
needs different seeds/temperatures per branch, which `n` cannot express.
Chat-message rendering (`tools`, `chat_template_kwargs` from A5) is not
wired into `/v1/fork` this round -- "fork at any token" is a token-count
claim, and none of the three gates need chat-message shaping.

## Gate 2: cost

RULER `niah_single` prompts (`bench/ruler/gen.py`, real text), ~869 /
~8059 / ~32636 tokens. Fork arm: one shared prompt, 4 branches, T=0,
`max_tokens=8`. Recompute arm: 4 distinct same-length prompts (a genuinely
independent baseline, not a forced cache-miss on identical bytes), 4
sequential `/v1/completions` calls, same settings. `BARO_TMAX=33024` for
all three lengths (one server session covers 1k/8k; 32k ran as its own
`gpu-wait` job per the protocol's own sizing decision).

| prefix | recompute wall (4x) | fork wall (1 prefill + 3 restores) | speedup | restore_s (branches 2-4) |
|---|---|---|---|---|
| ~1k (869) | 1.43 s | 0.56 s | 2.55x | 0.0025 / 0.0025 / 0.0025 s |
| ~8k (8059) | 12.31 s | 3.32 s | 3.71x | 0.0025 / 0.0025 / 0.0026 s |
| ~32k (32636) | 64.72 s | 16.76 s | 3.86x | 0.0023 / 0.0023 / 0.0022 s |

Every fork-arm branch 2-4's `cached_tokens` matched the prompt length
exactly (868/8058/32635) with `prefill_rows: 0` -- a real restore every
time, not a hidden re-prefill (the protocol's own void check). Predicted:
restore cost flat regardless of prefix length, because `CKPT_BYTES` is a
fixed constant (the model's own SSM/conv state, not the KV cache) --
confirmed: **restore time does not move (2.2-4.3 ms) across a 32x range of
prefix length**, while recompute-arm prefill scales from 0.29 s to 16.1 s
over the same range. This is the whole claim: prefix checkpoint restore is
the O(1) part, prefill is the part that scales, and forking pays the O(1)
part N-1 times instead of the scaling part N times.

Full bodies: `.work/b5-gate2/fork_{1024,8192,32768}.json`,
`recompute_{1024,8192,32768}_{0,1,2,3}.json`.
