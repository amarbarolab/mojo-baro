# Lane G0 report: every elementwise kernel through SPIR-V onto the Radeon R5 M330

Date 2026-09-17. Branch `lane-g0`, tooling commit `2f61363`. Brief:
`briefs/2026-09-17-g0-spirv-elementwise.md`.

## Verdict

**G0 PASSES. The kill line is not hit. Build G1, and build it smaller than planned.**

- All 13 `amar_*` kernels in `kernels/elementwise.mojo` run on the card from their Mojo IR and meet
  the parity bar: `tools/spirv-probe/run.sh` ended `PASS 13/13` on aihq-lab's R5 M330 (output pasted
  below), three repetitions per kernel on different data.
- **No kernel needs a phase split. Every kernel is 1 host dispatch** (kill line was 8). No
  construct lacks a lowering.
- The premise behind "G1 = general phase-splitting converter" was wrong. The earlier probe note said
  barriers and threadgroup memory do not exist in OpenCL SPIR-V. They do: `air.wg.barrier` is
  OpenCL `barrier()` (SPIR-V `OpControlBarrier`) and Metal addrspace(3) threadgroup memory is OpenCL
  local memory with the same address space number. Only `air.simd_shuffle_xor` has no counterpart
  (the card reports no sub-group support), and it lowers inside the kernel to local scratch memory
  plus barriers. The three-phase rmsnorm split (`rms2spv.py`, `host_rms.c`) is deleted.

## Lowering rules (all of them)

| Metal IR construct | lowering | phases |
|---|---|---|
| thread position args (`threadgroup_position_in_grid` etc.) | `get_group_id` / `get_local_id` / `get_local_size` / `get_global_size`, x and y | 0 |
| `thread_index_in_simdgroup` | `get_local_id(0) % 32`; the kernels already assume lane = tid % WARP_SIZE (`sums[tid // WARP_SIZE]`) | 0 |
| argument-buffer `load {ptr, ...}` + `extractvalue` | the buffer argument itself | 0 |
| addrspace(2) scalar args | 4-byte constant buffers | 0 |
| addrspace(3) `_gpu_shared_mem` global | kept verbatim, it is OpenCL local memory | 0 |
| `air.wg.barrier` | `barrier(CLK_LOCAL_MEM_FENCE)` | 0 |
| `air.simd_shuffle_xor.f32(v, mask)` | store v to local `scratch[lid]`; barrier; load `scratch[lid ^ mask]`; barrier. Order of the recursive doubling is preserved, so sums keep Mojo's summation order | 0 |
| `air.exp2/rsqrt/cos/sin/fmax`, `llvm.fabs/fma` | OpenCL builtins | 0 |
| `air.convert.*` | `sitofp` / `fptosi` | 0 |
| `bfloat`, `half` loads, stores, `fpext`, `fptrunc` | i16 buffers + `helpers.c` calls; any other use of the types is a loud `FAIL` | 0 |
| `fdiv float` | `q + fma(-q, y, x) / y` (see finding 1) | 0 |
| Apple float literals (`f0x...`, inexact decimals like `-3.4e+38`, `+qnan`) | exact LLVM hex literals | 0 |
| rope's `alloca [2 x ptr]` (Mojo's `log` returns through pointers) | removed by the clang `-O2` IR pass; without it `spirv-val` rejects the module | 0 |

Loop shapes: every loop is the strided per-thread scan `i = tid; while i < N; i += 256` (rope strides
by `block_dim`), a single back edge with a float or (float, i32) accumulator phi. The per-warp
gathers (`comptime for w in range(8)`, argmax's `range(256)`) arrive fully unrolled, which is why
argmax is 4.9k IR lines and an 87 KB SPIR-V module. `exp` arrives as `exp2(x * log2 e)`, `log` as an
inlined polynomial with `llvm.fma`. In q8 the shuffle chain sits inside a conditional (`row < M and
k < K`); that is legal under OpenCL only because the guard is uniform across a work-group for the
engine's dispatch (grid `(m, k // 32)`, block 32, K a multiple of 32). Metal has the same rule.

Note on the bf16 outputs: bf16 has 8 mantissa bits, so a last-ulp f32 difference before the cast can
legitimately flip the rounding by 0.8%. The check is therefore "the output is the correct bf16
rounding of some value within 1e-5 of the fp64 reference". In this run the window was never needed:
0 of 32008 outputs per run differed from the direct rounding of the reference. Rope uses the same
metric as `kernels/test_elementwise.mojo` (error relative to the pair norm), because a rotated
component can cancel to zero.

## Findings

1. **The card's float division is not IEEE.** `x / y` is bit-identical to `x * (1 / y)`: 288,596 of
   1,000,000 random quotients differ from the correctly rounded result. First full run was 12/13:
   q8 quantize missed 21 of 32768 codes, all exact ties (x equal to half the block maximum gives
   x / scale = 63.5 in IEEE, 63.4999962 on the card, so 63 instead of 64). One residual step,
   `q + fma(-q, y, x) / y`, measured 0 of 1,000,000 different, and the converter now applies it to
   every `fdiv`. Cost: two divisions and one fma per division. It is applied everywhere because
   the converter cannot know which divisions feed a rounding; G1 should decide whether to keep that
   or make it opt-in per kernel. Any identity gate in G3 against an IEEE reference depends on it.
2. bf16 and f16 need no hardware support: integer helpers are bit-identical to native casts (CPU
   preflight, and on the card: embed bit-exact, q8 f16 scales exact).
3. Mojo's Metal route rejects f64. A side scan for the G1 estimate tried
   `kernels/test_ssm_block.mojo` with the same emit flags and the build failed at "LLVM ERROR:
   Failed to verify LLVM IR for Metal" (`std.math.log1p` goes through `air.convert.f.f64` and
   `llvm.fma.f64`). Not chased, outside G0, the first thing G2 meets on the SSM side.
   (Correction: `kernels/test_gemm.mojo` wrote no kernel `.ll` simply because it is the CPU
   AmarBaro test. The q4 GEMV emits fine, see the addendum.)

## What G0 did not measure

- **No timing.** Nothing here says the lowered kernels are fast. `warp.sum` costs 10 barriers and
  10 local-memory round trips as lowered, softmax 23 barriers in total.
- Early return before a collective is only safe while the guard is uniform per work-group (true for
  the engine's q8 dispatch, not checked by the converter).
- Shuffles inside loops did not occur in these 13 kernels. The two-barrier form is safe there as
  long as the trip count is uniform per work-group, but that is argued, not run.
- The name resolver and every regex in `air2spv.py` are fitted to Mojo 1.0.0's Metal IR text, an
  internal format that may change per release. `run.sh` fails loudly when it does.
- Local memory on the card is 32 KiB; the largest use here is argmax at 2 KiB plus 1 KiB scratch.

## Size estimate for G1

The L-to-XL item in the earlier note (phase splitting with liveness spill across every barrier and
an idiom table for warp collectives) is not needed. What remains:

| item | size | why |
|---|---|---|
| Converter generalisation: more `air.*` math and integer intrinsics, i32/i64 and vector shuffles, other simd collectives, `<N x T>` vector types if the GEMMs use them | M (60 to 150 LOC on top of the 204) | table rows plus a vector-type pass; unknown count until the GEMM IR exists (finding 3) |
| Get GEMM / SSM kernels to emit at all through the Metal route (f64 in `log1p`, test_gemm writing no `.ll`) | unknown, S if it is a probe-file issue, a real blocker if the kernels need f64 | this, not the converter, is the largest G1/G2 risk |
| Barrier cost reduction: ping-pong scratch (one barrier per shuffle, order preserved) or a `warp.sum` idiom (2 barriers, changes summation order) | S, only after a timing run says it matters | harness before kernel |
| Work-group uniformity check for guards and loops around collectives | S | turns the two argued items above into converter errors |
| Host runtime for the engine on the lab box (buffer pool, kernel cache, arg binding, 512 MiB max buffer) | L, but it belongs to G2/G3, not to the converter | `host.c` is a test harness, not a runtime |

Converter total: **M, not L-XL**, with one unsized risk (kernels that do not emit through the Metal
route). Recommended first G1 step: emit the q4 GEMV IR and run `inventory.py` on it before writing
any code, then a timing harness on the card for rmsnorm and softmax before touching barrier counts.

## Addendum, same day: G1 scouting, the engine's q4 GEMV runs on the card

Done after the verdict above, on the maintainer's "go", as the first G1 step the report recommended.
`probe_gemv.mojo` instantiates the pair `gemm_q4` dispatches at m = 1:
`amar_matmul_skinny_q4rowb[2, 1]` and `amar_skinny_reduce[.., 1]`. `run.sh gemv` on the card:

```
amar_matmul_skinny_q4rowb phases=1 barriers=10
amar_skinny_reduce phases=1 barriers=0
PASS amar_matmul_skinny_q4rowb x3  max err relative to sum|terms| 9.114e-09
PASS amar_skinny_reduce x3  exact copy of the GEMV partials, err 0.000e+00
PASS 2/2
```

Shape 1024 rows x 4096 columns, ggml Q4_0 layout, fp64 reference, error measured against the sum of
the absolute terms of each dot product (a dot product can cancel, so plain relative error is not
meaningful). The 13-kernel gate and the reverse arm were re-run after these changes: still
`PASS 13/13` and `PASS reverse-arm`.

| kernel | IR lines | new constructs vs the 13 | converter change |
|---|---|---|---|
| amar_matmul_skinny_q4rowb | 1440 | `<16 x float>` / `<8 x i32>` / `<4 x i32>` vector code (322 uses of `<16 x float>`), `load <16 x bfloat>` + `bitcast` to `<8 x i32>` (the kernel unpacks bf16 by shift and mask itself), `load half` + `fpext`, `air.convert.f.v16f32.u.v16i8`, `llvm.fma.v16f32`, 8 allocas (InlineArray), 4 loops | vector forms of the type, convert and builtin tables, a `baro_f16_to_f32` helper: about 35 lines |
| amar_skinny_reduce | 68 | none | none |

Two things this turned up:

4. **clang 22.1.8 `-O2` SPIR-V codegen emits invalid SPIR-V for the GEMV**: it drops `trunc i64 to
   i32` and feeds the 64-bit local id into 32-bit ops (`OpBitwiseAnd %uint %ulong_value`), caught
   by `spirv-val`. Same at `-O1`, `-O3`, `-Os`. Optimizing to IR first and compiling that at `-O0`
   is valid, so `run.sh` now does the two steps for every kernel. `spirv-val` stays in the loop as
   the guard.
5. **The GEMV's early return is not uniform per work-group when n is not a multiple of 8.** A
   work-group is 8 rows (256 threads); rows past n return before the `warp.sum` barriers while the
   other rows in the group reach them, which OpenCL leaves undefined (Metal too). The probe uses
   n = 1024. G1 needs either n padded to 8 rows at dispatch or a converter rule that turns such a
   guard into "compute, but do not write".

**Revised G1 converter estimate: S to M, and the unsized risk is gone for the GEMV path.** The q4
GEMV needed about 35 converter lines and no new mechanism. Still open: the SSM kernels' f64 on the
Metal route (finding 3), timing (nothing measured; radeonsi will scalarize the 16-wide vectors, and
the lane split of one row across 32 threads with 10 barriers is a design made for the 7900 XTX, not
for this card), and the host runtime (L, G2/G3).

## Reproduce

```

```

`/root/g0/`; `/root/mojo-baro` was not touched. The workstation GPU was not used, no gpu-wait jobs.
