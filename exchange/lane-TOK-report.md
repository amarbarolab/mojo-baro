## Flags (read first)

- **Two real bugs found wiring `llama-bpe`, both are design-call-adjacent fixes, not scope
  creep — the item's own gate (exact ids vs `llama-tokenize`) fails without them.**
  `llama3`/`llama-bpe` GGUFs carry no `tokenizer.ggml.add_bos_token` key; llama.cpp's
  `llm_tokenizer_bpe` constructor hardcodes `add_bos = true` for that pre-type regardless
  (`llama-vocab.cpp:2148-2159`), so the existing "default false unless the key says otherwise"
  read was wrong specifically for this pre. Same pre-type sets `ignore_merges`: a whole
  regex-split piece that is already a single vocab token is emitted directly, skipping BPE
  merges — needed because Llama-3.2's vocab has 1-3 digit number tokens with no merge chain
  that reaches them. Both gated: 0 id mismatches on Llama-3.2-1B across the hard set + 20 prompts.
- **Files touched outside `serve/tokenizer.mojo`:** `tools/test_tokenizer_mojo.py` (the gate
  script itself needed two fixes to be correct for a *second* target, see below — it previously
  only ever ran against Qwythos) and `docs/TOKENIZER.md` (preregistration + gate section, as the
  plan's rules require). No kernel, engine, or pack-path files touched.
- **Test-harness bug 1, fixed:** `test_tokenizer_mojo.py` read the 20 prompt references from
  `bench/mtp-prompts/*.tokens`, which are Qwythos-specific ids — the wrong reference for any
  other target. Now recomputed live via `llama-tokenize` on `--gguf`, same as the hard set
  already did. Verified this is a no-op for the existing regression pair (still 62/62, see below).
- **Test-harness bug 2, fixed:** the script inferred `add_bos` for its `decode(encode(x))==x`
  round-trip check by checking whether some case's *reference* ids happened to start with
  `bos_id` — a false positive on Qwen2.5, whose `bos_token_id` is numerically the same id as
  `<|endoftext|>`, and whose `special-eot` hard-set case legitimately starts with that literal
  token. Fixed to read `add_bos_token` (or the `llama3`/`llama-bpe` pre-type default) straight
  from GGUF metadata. This also fixed the standalone `"empty"` case, which needs `[bos_id]`
  rather than `[]` on any add_bos=true model.
- **`HARD_SET`'s own `"empty"` entry was a duplicate of the dedicated `("empty", ...)` case with
  a different (and, for add_bos=true models, wrong) expectation hardcoded via `encode_ref`'s
  own empty-string special case.** Removed it from `HARD_SET`; the dedicated case covers it.
  This is why the regression pair's case count drops from 63 to 62 with no loss of coverage.
  Also: the plan's "41-case hard set" was off by one — counted precisely (not via the grep that
  inflated it), the real `HARD_SET` was 40 entries before this fix, 39 after.
- Kernel files carry no comments per repo CLAUDE.md; not applicable here (no kernel files touched).
